   Add the four callees that the toggle and dispatcher branches require:

   omarchy-monitor-base sync|get|list
     Allocates and persists stable name-keyed workspace bases in
     ~/.local/state/omarchy/monitor-bases.json. Keyed by monitor OS name
     (e.g. "DP-1"), not transient Hyprland id, to survive hotplug
     reassignment (hyprwm/Hyprland#2601). Called by workspace-global.lua.

   omarchy-hyprland-workspace-global-switch <slot>
     Dispatches all monitors to their slot-N workspace by reading the bases
     file and issuing one hl.dsp.focus dispatch per monitor. Called by
     omarchy-switch-to-aw in global mode.

   omarchy-hyprland-workspace-global-move-window <slot>
     Reads the focused window's monitor name, looks up its stable base, and
     silently moves the window to base+slot. Called by omarchy-move-window-to-aw
     in global mode.

   omarchy-ensure-workspaces
     Delayed post-init verifier: sleeps 1s, checks that all expected workspace
     IDs exist (materialised by Hyprland), re-dispatches any that are missing.
     Called as a background job by workspace-global.lua at config load.

3. Bar slot/focus mapping (llstrk issue omacom#3)
   Rewrite Workspaces.qml to be global-mode aware:
   - Detects the toggle flag via FileView.exists (reactive, live toggle support).
   - Adds slotOfId(): maps raw workspace IDs back to logical slots 1–10 using
     ((id - 1) % 10) + 1, so WS 12 (monitor-2 slot 2) correctly maps to slot 2.
   - slotOccupied() and slotFocused() check ALL raw IDs that map to a slot,
     so focused/occupied state is correct when the active workspace is >10.
   - focusWorkspace() routes through omarchy-switch-to-aw in global mode
     (all-monitor sync) vs direct hyprctl in local mode.
   - Local mode (toggle off) is unchanged: slot == raw ID, direct dispatch.

No behavior change in local mode. All changes are additive and gated on the
global-mode flag file.

omarchy-monitor-base sync never allocates a base

allocate_bases runs python3 - ... <<'PYEOF'. The heredoc becomes Python's stdin to supply the program, so the monitor names piped in at line 130 never reach sys.stdin at line 84.

Isolated run, synthetic hyprctl reporting eDP-1 and HDMI-A-1:
sync as shipped              -> stdout empty, bases file {}
same Python, names on stdin  -> "eDP-1 0", "HDMI-A-1 10"

Impact: the Lua module always falls back to monitor.id * 10, the global switch helper only focuses the raw slot, and omarchy-ensure-workspaces exits immediately. This is the impact the earlier "missing helpers" finding described.

Suggested change: pass the names as arguments (for example names = sys.argv[2:]) or run the program with -c, so stdin stays free for the data.

The move helper looks up a numeric monitor ID as a name

omarchy-hyprland-workspace-global-move-window reads monitor from hyprctl activewindow -j. In Hyprland 0.56.2 that field is the numeric monitor ID (src/debug/HyprCtl.cpp, window JSON), while the bases map is keyed by name.

Isolated run, map {"eDP-1":0,"HDMI-A-1":10}, slot 2:
monitor: 1           (Hyprland shape) -> move to workspace "2"
monitor: "HDMI-A-1"  (control)        -> move to workspace "12"

Impact: even with a populated map, windows move to raw workspace N, which the global rules bind to the base-0 monitor, so the window leaves its monitor.

Suggested change: take the monitor name from hyprctl activeworkspace -j or from the focused entry of hyprctl monitors -j.

The bar's global-mode flag can never become true

Workspaces.qml has two independent blockers:

  1. StandardPaths belongs to the QtCore QML module, which the file does not import, so globalFlagPath does not resolve to the flag file.
  2. Quickshell's FileView has no exists property (checked in the Quickshell revision Omarchy packages and in upstream sources). globalModeActive therefore stays false. Even the real loaded property would not react to the file appearing, because watchChanges is not set.

Impact: slot mapping, cross-monitor occupancy and click routing through omarchy-switch-to-aw never activate, so workspace 12 still lights no button.

Suggested change: follow the existing flag pattern in shell/Commons/Style.qml (windowNoGapsToggle): build the path with Quickshell.env("HOME"), set watchChanges: true, and derive the flag from load/failure/change signals, or watch the toggles directory as Bar.qml does.

Config reloads stall for about 5 seconds while the toggle is on

The module calls io.popen("omarchy-monitor-base sync") during config evaluation, and the helper runs hyprctl monitors -j.

hyprctl reload / autoreload
  -> Hyprland event loop runs the config synchronously
     -> io.popen: omarchy-monitor-base sync
        -> hyprctl monitors -j   (needs the same event loop to answer)
           -> waits for the hyprctl 5 s receive timeout, returns no monitors

Source-derived from Hyprland 0.56.2 (HyprCtl.cpp socket handling and reloadRequest, hyprctl/src/main.cpp timeout), not observed natively. At login the socket does not exist yet, so the call fails quickly instead.

Impact: input and rendering pause on every reload with the flag enabled, starting with the reload that omarchy-hyprland-toggle workspace-global on issues. That command's own hyprctl reload may also time out and report failure after the flag was already copied. The module still receives no bases.

Suggested change: avoid IPC from config evaluation. The module already has hl.get_monitors() names, so allocate in Lua, or pass those names to the helper as arguments.

Default workspace keybindings bypass the new commands

default/hypr/bindings/tiling.lua still binds SUPER+N and SUPER+SHIFT+N to raw workspace N. Nothing calls omarchy-move-window-to-aw, and the only caller of omarchy-switch-to-aw is the bar click path above.

Impact: in global mode, SUPER+SHIFT+2 on a base-10 monitor sends the window to workspace 2 on the base-0 monitor instead of workspace 12. Switching relies only on the Lua workspace.active hook.

Suggested change: route these bindings through the global-aware commands (or Lua equivalents) when the flag is on, or document the intended binding setup.

Hotplug is not picked up until a reload

The module builds its bases, monitor list and workspace rules once per config evaluation (lines 53–128) and subscribes only to workspace.active (line 234). Hyprland 0.56.2 does not reload the config on hotplug, and omarchy-hyprland-monitor-watch reloads only in specific clamshell, mirror and mode cases.

Impact: a newly connected monitor is not synced, and a disconnected monitor's stale entry still dispatches its workspace, which Hyprland has moved to another monitor. This conflicts with the stated hotplug support. It becomes visible once the allocator works.

Suggested change: handle Hyprland's Lua monitor.added / monitor.removed events to refresh the map and live monitor set, and dispatch only to connected monitors.

Suggested change: dispatch the originating monitor last, or refocus it after syncing.

  -> dispatches focus 11, 12, ... 20, then 1
control: workspaces 1-20 exist -> no dispatch

Source-derived consequence: each missing workspace is created on the focused monitor, the workspace.active hook syncs every monitor to it, and the final dispatch leaves every monitor on slot 1. The switch helper loops over the same saved list.

Impact: for anyone whose saved bases include a display that is no longer connected (for example after one docking session), every reload, login and hotplug cycles through slots and leaves the desktop on slot 1. This became reachable in this commit, because the bases file was always empty before.

Suggested change: in both helpers, iterate only monitors currently reported by hyprctl monitors -j, and drop the unconditional return to workspace 1.

New in this revision

The bar can miss the first enable on a fresh setup

Workspaces.qml watches ~/.local/state/omarchy/toggles/hypr once, when the widget is created. Quickshell's FileView also watches the parent directory, but Qt cannot watch a path that does not exist. If neither toggles/hypr nor toggles exists at bar startup, nothing is watched. omarchy-hyprland-toggle creates them later, and the bar is not notified. Source-derived. Nothing under install/ or migrations/ creates these directories, so a fresh install where no toggle has been used yet is affected.

Impact: Hyprland runs in global mode while the bar keeps the local mapping until the shell restarts. Secondary monitors' workspaces do not light a button, and bar clicks go to raw workspace N.

Suggested change: have the toggle command nudge the shell over IPC, as omarchy-toggle-bar does for the bar-off flag, or create toggles/hypr during install or in a migration.

The move helper's fallback is now unreachable

This commit added set -euo pipefail (line 12). When the focused monitor is missing from the bases map, the embedded Python exits 1 and TARGET_WS=$(...) ends the script before the raw-slot fallback runs. Isolated run: bases {eDP-1: 0}, focused HDMI-A-1, so the helper exits 1 with no move. At caff3e03ef34 it moved the window to "2".

Impact: a monitor not yet in the map gets no move at all. The Lua allocator normally keeps connected monitors in the map, so this is an edge case.

Suggested change: if ! TARGET_WS=$(...); then around the assignment, with the fallback inside.

Workspace IDs above 99 stop syncing

The Lua hook ignores workspace IDs above 99 (workspace-global.lua:232), and the bar maps them to no slot (Workspaces.qml:52). The allocators have no cap and never free bases, so the tenth distinct monitor name gets base 90, and later names start at 100. Source-derived.

Impact: on those monitors, some or all slots do not sync other monitors and show no focus or occupancy in the bar. Physical connectors rarely reach ten names. Unnamed headless outputs get a new HEADLESS-n name each time, so a virtual-display workflow can reach this, and the state is permanent.

Suggested change: derive the slot from the bases map instead of a fixed 99 bound, or skip or reuse bases for headless outputs.

Test-only failures: these do not affect runtime behavior. The new monitor-base-test.sh fails at this head. Its last case expects sync to print persisted bases when hyprctl fails, but sync exits 1 there, so the file aborts after 8 of 9 checks. Separately, bin-style-test.sh rejects the raw command -v hyprctl at omarchy-monitor-base:119; that has failed since caff3e03ef34. Using omarchy-cmd-missing or dropping the check fixes it. omarchy-hyprland-workspace-global-move-window also lacks # omarchy:hidden=true.

Optional test improvement: the switch and move tests replace the global helpers with stubs and pass unchanged at caff3e03ef34, where the move helper still sent windows to the wrong workspace. Running the real move helper against a stub hyprctl with a focused non-base-0 monitor would catch that regression.
